# Food Intelligence Platform — database design

Status: **TARGET BACKEND 2.0 — logical design, not executable DDL**. Legacy MongoDB `BistroDB` is reference only; its shapes do not define this schema. [PRODUCT_DOMAIN.md](PRODUCT_DOMAIN.md) is authoritative for domain rules. No PostgreSQL tables or migrations exist. The original 25 candidates remain documented, with eight deferred; four justified additions support authentication, location access, and bounded returns. That is **21 MVP table designs and eight deferred candidates**, not 29 tables to build now. [Migration plan](MIGRATION_PLAN.md) is conditional; [ER diagram](docs/content/architecture/diagrams.md) distinguishes scope.

## Shared conventions

UUID primary keys; `created_at` as timestamptz on every table; `updated_at` on mutable records. Business-scoped rows carry `business_id NOT NULL`. Parent tables expose unique `(business_id, id)` keys, and children use composite foreign keys to prevent cross-business references. Global users/roles are exceptions, not implicitly tenant-owned. Never accept business scope from a body without verified membership.

Global identity data is not a tenant directory. `auth_sessions` and `auth_action_tokens` belong to users, not businesses. All other operational records have explicit business ownership. Orders/waste carry `location_id`; grants in `membership_locations` limit staff/viewer access. Repository reads/aggregates include the authorized location set. Composite references and fresh application authorization are required; RLS is not assumed to exist. Scope applies equally to future cache keys, jobs, reports, sockets, and model datasets.

Exact `numeric(18,6)` quantities in one declared product base unit; positive inbound quantities and signed ledger deltas. Units: piece/kg/gram/litre/ml/package; piece/package require integral counts. Allow exact kg↔gram and litre↔ml conversions only. Exact `numeric(20,6)` unit costs and monetary snapshots are rounded to the business currency precision at line boundaries using decimal half-up rounding as an explicit MVP assumption. Single currency per business; no mixed-unit or mixed-currency sums. Tax-exclusive prices use a snapshotted rate on post-discount value; validate actual jurisdiction/rates before production.

Use timestamptz for events and business timezone for reporting. Expiry is an exclusive `expires_at` instant; date-only labels map to the next local day's start under the documented, reviewable label assumption. Nullable expiry means unknown or explicitly nonperishable, never implicitly safe. Archive catalog/users where history requires preservation. Historical sales/returns/waste/movements/allocations are not cascade-deleted.

**MVP:** businesses, users, roles, business_memberships, membership_locations, auth_sessions, auth_action_tokens, products, categories, suppliers, inventory_locations, inventory, inventory_batches, inventory_movements, orders, sale_items, sale_item_batch_allocations, sale_returns, sale_return_items, discounts, waste_records.

**Deferred:** payments, payment_webhook_events, forecast_runs, forecast_predictions, carts, cart_items, reviews, outbox_events. Do not generate these tables/migrations until the corresponding feature is approved. Original candidates are retained as reference rather than erased.

The four additions are required by selected domain assumptions: expiring single-use authentication actions, normalized location grants, and immutable return header/lines to bound repeated refunds. No invitation/custom-permission/subscription tables are needed in MVP. Authentication is local-password by explicit assumption; external federation is deferred. Optional imported supplier/category/review fields are never guessed.

## Transaction invariants

1. Inventory service acquires inventory rows in a stable order, then eligible batches ordered by expiry (known expiry first), received time, and UUID. Exclude expired, quarantined, and unknown-expiry perishable stock. Transaction retries are bounded for deadlock/serialization failures.
2. Stock operations change batch balance, inventory projection, immutable movement(s), and relevant order/waste/return records together. Outbox is deferred until asynchronous integration exists. Cross-row totals are verified in transactions; ordinary CHECK constraints cannot enforce sums across rows. Returned-goods disposal has a return/waste fact but no second stock decrement.
3. For each batch, sum of signed ledger deltas equals remaining quantity. For each inventory row, sum of batch quantities equals on-hand quantity. Reserved stock is not implemented in this baseline; available saleable stock excludes ineligible batches. On-hand and saleable quantities must not be conflated.
4. PURCHASE is positive, SALE/WASTE negative, ADJUSTMENT signed with reason, RETURN positive only after an inspected restock decision. TRANSFER writes equal-and-opposite movements in one transaction, retaining lot, expiry, and cost provenance. A correlation ID groups the pair without a new transfer table initially.
5. Allocation quantities sum to each completed sale item's quantity, and its sale movements agree with allocations. Waste cost is quantity times immutable cost snapshot under rounding policy. Order totals equal item totals. No duplicate stock mutation on a retried request.
6. Product and currency must match across order, sale items, allocations, batches, and payments. A cross-tenant relationship is rejected even if the referenced UUID exists.
7. Return commands lock original sale items and allocations in stable order before checking cumulative quantities and money. Cap quantity per allocation and money per original sale item; proportional reversal rounding assigns remaining cents to the final return. Restock inspected eligible units into the original batch with original cost/expiry and a same-business return-item FK. Waste quantities must agree with disposed return quantities and cannot also be restocked. Reject over-return and changed-payload idempotency replay. Deferred payments require separate webhook reconciliation; no provider call is in MVP.
8. Audit corrections use compensating records/status transitions. Do not rewrite completed historical quantities or cost snapshots. Authorization audit metadata belongs in structured security logs with defined retention; the stock ledger is not a complete security audit log.
9. Serialize owner grants/removals on the business row so concurrent demotions cannot remove the last owner. Role grants obey the actor/target role matrix; ownership, tenant and location checks apply even when valid UUIDs are supplied.

## MVP sales and deferred payments

MVP staff submit a sale; the server calculates snapshots and commits completed order/items/FEFO allocations/stock in one transaction. No cart, reservation, online checkout, or payment authorization is required. Returns record bounded financial reversals and inspected stock disposition; they do not prove cash has been refunded. This is operational recording, not payment reconciliation or fiscal invoicing.

Future online payment support must separately define provider capabilities, authorization/capture/fulfillment and compensation. Stripe Test Mode is then the initial restaurant-order adapter, not SaaS subscription billing. No PostgreSQL transaction can roll back an external charge.

## Query and history design

Expiry: authorized business/location, positive balance, expiry window. Low stock: inventory compared with reorder level. Ledger/waste: authorized business/location/time with cursor pagination. Sales: completed orders by business/location/completed_at joined to items; aggregate before joining allocations to avoid duplicated revenue. Cost uses allocation snapshots. Report gross, discounts, net before tax, tax, returns, and waste loss separately. Revenue after returns uses net reversals, not tax-inclusive return totals. Payment receipt reporting is deferred.

MVP stock-waste percentage is STOCK-origin wasted quantity divided by completed sold quantity plus STOCK-origin waste, using the same period/product/base unit. Denominator zero yields null. Label that it uses gross sold units, not return-adjusted units, and is not shrinkage. CUSTOMER_RETURN disposal is reported separately to avoid double-counting stock loss. Return-period financial reversals are shown separately from sale-period revenue. No mixed-currency totals or out-of-scope location leakage.

Financial loss estimates must not add disposed customer-return cost on top of the same cost already attributed to the original sale. Reclassify that amount if showing returned-food waste separately. Inspected restocks reverse the original allocated cost for the returned quantity. MVP reporting is operational, not a full accounting ledger.

Future forecasting reads verified sales and explicitly defined returns/stockout/closure coverage, never treating unknown periods as zero demand. Persist run provenance/predictions only when that feature is approved. Initial analytics derive from immutable facts; no speculative aggregate tables.

## Migrations and validation

Future Drizzle schema/migrations live under `apps/api/src/database/` and `apps/api/drizzle/`; only feature-approved MVP tables are created. Review SQL and test empty/upgrade/restore paths without destructive synchronization. Tests must cover session replay/revocation, last-owner protection, location grants, cross-tenant references, concurrent FEFO/returns, stock conservation, tax/discount rounding, returned-goods disposal, idempotency, and rollback. Provider/webhook tests wait for the deferred payments feature. No migrations/tests are created now.
